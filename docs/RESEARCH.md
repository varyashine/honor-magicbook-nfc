# История исследования (как дошли до вердикта)

Хронология реверс-кампании «записать свой URL во встроенную NFC-метку
HONOR MagicBook», октябрь 2026. Цель: собственный адрес вместо
заводского `hihonor.com` при тапе телефоном.

## Этап 1. Разбор vendor-стека

Официальный софт «One-Tap» (Honor PCManager NFC) состоит из драйвера
`SpbNfcDriver.sys` и библиотеки `nfc_midware.dll`. Оба были декомпилированы в Ghidra
(headless, скрипт-экспорт декомпилата):

- **nfc_midware.dll** (3044 функции, PDB-имена на месте): полный протокол.
  `fm11n_init` (проверка головы `1d 19 db…`, sleep 10 мс, bitlock:
  `val|0xf8` @`0x000A`, `0xff` @`0x000B`, `{00 00 ff ff}` @`0x0388`),
  `UpdateNfcData`: запись кусками 16 байт от `0x0010`, лимит `0x378`,
  без верификации; `WriteNfcContent` → `WriteFile` в `\\.\SPBNFCDRIVER`.
- **SpbNfcDriver.sys**: диспетчер записи по `buf[1]`: зоны
  `0x10/0x20/0x30/0x40` с SHA-256-верификацией против вшитых дайджестов.

## Этап 2. Взлом дайджестов

Перебор входов дал: все 4 дайджеста это SHA-256 кусков заводского URL
`"www.hihon"`, `"or.com/global/su"`, `"pport/magic_link"`, `"_welcome/"`.
Вывод: драйвер пропускает только заводской URL и не может записать другой
адрес. Но это программный фильтр Windows, а не ограничение чипа.

## Этап 3. Прямой I²C в обход драйвера

Чистый Python (fcntl/ctypes, ioctl `I2C_RDWR`): чтение работает без
ошибок, запись в NDEF-зону получает **NAK (errno 121)** на любой контент, включая байт-в-байт
заводской. 154 попытки при активном RF-поле (телефон читает метку):
само по себе поле запись не разблокирует. Перебором адресов выяснено, что
ACK получают только `0x30, 0x50, 0x70-0x8D (токен), 0xA0, 0xD0…`, то есть
ровно то, что нужно Honor для обновления токена.

## Этап 4. Охота за даташитом

Первая гипотеза (FM11NT021) не подтвердилась: это чисто RF-метка Type 2
без I²C. Класс чипа определили по косвенным признакам (Type 4/ISO-DEP в
NFC Tools, I²C, IRQ, FIFO): семейство **FM11NC08**. Полной документации в
открытом доступе нет.

## Этап 5. Находка на GitHub

Свежий (сентябрь 2026) проект **ZhuRuoLing/magicbookartd**, Linux-демон
для MagicBook Art 14 с функцией `nfc write-url`. Реверс драйвера автора
совпал с нашим байт-в-байт (те же зоны, те же дайджесты, тот же вывод:
«фильтр Windows ≠ ограничение чипа»), и, по словам автора, на его машине
запись работает. В документации проекта указано точное имя чипа: **FM11NT082C-NTCZ-…**.

## Этап 6. Вердикт

Даташит FM11NT082C, таблица заказа:

- `NTCZ`: статические лок-биты с завода `0000h` → пишется;
- `NTCI`: `FFFFh` → заблокирован OTP-битами навсегда.

MagicBook Art 14 = NTCZ. MagicBook 14 Pro 2023 (эта машина) = NTCI: локи
`ff ff` по адресу `0x000A`, NAK на любую запись в запертые страницы.
Сбросить их нельзя: это одноразовые биты, в этом их смысл.

## Выводы

- Защита многослойная (OTP в чипе + фильтр в драйвере + RF-стек), так что
  на NTCI-машинах метка всегда будет указывать на `hihonor.com`.
- Решающим оказалось не вскрытие драйвера, а лок-байты и таблица заказа
  из даташита: их стоит проверять первым делом.
- Если нужен свой URL при касании ноутбука, проще всего наклеить стикер
  NTAG213 в центр тачпада.
