# Протокол доступа к FM11NT082C (NTAG0001) по I²C

Всё ниже: результат реверса вендорского стека (SpbNfcDriver.sys + nfc_midware.dll)
и экспериментов на реальной машине (MagicBook 14 Pro 2023), сверено с реверсом
[magicbookartd](https://github.com/ZhuRuoLing/magicbookartd) (MagicBook Art 14)
и даташитом FM11NT082C.

## Идентификация

- ACPI HID: `NTAG0001`, в Linux адаптер `/sys/bus/i2c/devices/i2c-NTAG0001:00`.
- I²C-адрес: `0x57` (7-bit). На той же шине HID-устройство `0x2B`, его не трогать.
- Признак живого чипа: чтение 16 байт с `0x0000` возвращает
  `1d 19 db 57 3c 07 00 10 2b b0 …`.

## Карта памяти

| Адрес | Назначение |
|---|---|
| `0x0000` | Заголовок (сигнатура `1d 19 db 57 3c 07 00 10`; байты 8-9 служебные) |
| `0x000A` | Статические лок-байты (CL Static Lock Bytes): `ff ff` у NTCI, `00 00` у NTCZ |
| `0x000C` | CC Type 2: `e1 10 6d 00` (mapping 1.0, 0x6D·8 = 872 байт данных) |
| `0x0010` | Начало пользовательской области; NDEF TLV `03 8c` (сообщение 140 байт) |
| `0x0012` | Заводская NDEF: URI-запись `91 01 33 55 04` + `https://www.hihonor.com/global/support/magic_link_welcome/` |
| `0x0048` | MIME-запись `application/vnd.huawei.handoff.ndfmsg` (токен handoff) |
| `0x0378` | Конец пользовательской области (0x0010 + 872) |
| `0x0388` | Регистры: `dyVal` (4 б.), `fdMode` (байт @ `0x038C`, заводское `06`) |

Заводская NDEF: TLV `03 8c 91 01 33 55 04 …`: тип `U` (URI), префикс `04` =
`https://`. UID, который показывают телефоны (`1D:19:DB:3C:07:00:10`), это
первые байты блока 0, чип отдаёт начало EEPROM как UID.

## Чтение

Стандартная транзакция Windows-драйвера (STOP-разделённая):

1. `write [addr_hi, addr_lo]`: установка указателя (передаётся как запись
   длины 2, поэтому диспетчер драйвера пропускает 2-байтовые записи).
2. `read N`: N байт с текущего указателя, указатель автоинкрементится.

Работает и combined-транзакция (repeated START, ioctl `I2C_RDWR`):
`[addr_hi, addr_lo] + read`. Для надёжности утилита читает каждый блок
дважды и сверяет.

## Запись

Одна транзакция: `[addr_hi, addr_lo] + данные (≤16 байт)` по выровненному
адресу. Время программирования 10 мс (даташит); утилита ждёт 20 мс и
перечитывает записанное. Правила безопасности:

- не повторять упавшую запись вслепую (драйвер и magicbookartd делают так же);
- после серии записей чип может временно отвечать NAK даже на чтение,
  помогает пауза 10-30 секунд;
- порядок замены NDEF: сначала обнулить длину TLV (записать первый блок с
  `len=0`), перезаписать изменённые блоки, в самом конце записать первый
  блок с новой длиной (это и публикует сообщение), затем полная проверка.

## Защита

Три независимых слоя:

1. **Аппаратный (главный)**: статические лок-биты `0x000A-0x000B` и
   динамические лок-биты. OTP: устанавливаются на заводе, сбросу не
   подлежат. NTCI = `ff ff`: заперто всё, кроме области токена
   (`0x0070-0x008D`), которую софт Honor ротирует для handoff.
2. **Драйвер**: диспетчер `FUN_140003160` по младшему байту адреса
   (`buf[1]`): зоны `0x10/0x20/0x30/0x40` пропускаются только если SHA-256
   данных совпадает с вшитыми дайджестами (`DAT_140006170/190/1b0/1d0`),
   то есть SHA-256 от кусков заводского URL. Зоны `0x50/0x60` свободны,
   `0x70/0x80/0x90` работают как «hash-in-place». Регистровые команды (`buf[0]∈{0,3}`):
   `0x0A→|0xf8`, `0x0B→0xff`, `0x88→{00 00 ff ff}`, `0x8C→pass`.
   Проверка данных: длина ровно 0x12 (18 = 2 адрес + 16 данных).
3. **RF**: Type 4 (ISO-DEP) стек чипа. Запись с телефона на моей машине
   отклоняется; вероятно, нужна сессия handoff от софта Honor, но это не
   проверено.

## Ошибочная гипотеза, которую стоит похоронить

**FM11NT021 не тот чип.** Это чисто бесконтактная Type 2 метка (144 байта,
без I²C). Встроенный чип MagicBook: FM11NT082C (близкое семейство, но
другой интерфейсный набор). Полной карты регистров FM11NC08/FM11NT082C
в открытом доступе я не нашёл; публичный даташит описывает параметры и таблицу заказа, но не протокол.
Протокол выше восстановлен из поведения вендорского стека. Чтение
проверено на моей машине, запись по данным magicbookartd на MagicBook
Art 14.
